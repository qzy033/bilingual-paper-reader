# 使用说明（详细版）

> 这份文档讲清楚三件事：**怎么把一篇 PDF 变成一本可读的双语书**、**AI 具体翻译了哪些内容**、
> **出了问题怎么查**。格式字段的权威定义在 [`../reader/FORMAT.md`](../reader/FORMAT.md)。

---

## 0. 两条路线，先选一条

| | 路线 A：让 AI Agent 读论文、直接写数据 | 路线 B：跑脚本批量翻译 |
|---|---|---|
| 适合 | 想读**精**：要好的导读、术语解释、图表说明 | 想读**快**：长文、多篇、先出草稿 |
| 谁来做 | Claude Code / Codex / Cursor / Cline 等能读写本地文件的 agent | 本仓库的 `tools/translate.py` |
| 产出 | 分节、配对、术语、导读、图注、表格，一次到位 | 每段一个译文；术语标记和术语表靠第二、三步补 |
| 质量 | 高（能判断哪里该拆句、哪个词值得解释） | 中（逐段直译，结构完全照搬抽出来的骨架） |
| 成本 | 你的 agent 订阅 | 按 token 付费，一篇几分钱 |

**推荐 A，B 作为补充。** 这个项目本身就是这么做的：先抽文本，然后由 agent 逐节翻译、
加术语、补图注，最后用 `build_paper.py` 校验。

两条路线可以混用：A 翻正文，B 补术语标记；或者 B 先出草稿，A 再润色。

---

## 1. 准备

- **Python 3.9+**（路线 B 与打包需要；纯阅读不需要，解压双击即可）
- **PyMuPDF**：`python -m pip install pymupdf`（抽 PDF 用）
- **翻译 API**（仅路线 B）：任何 OpenAI 兼容端点，见 §3.1
- **能读写本地文件的 AI agent**（仅路线 A）

```
仓库根目录
├─ make.ps1 / make.sh     一条命令走完 4 步
├─ build_paper.py         校验并生成 reader/papers/library.js
├─ tools/
│  ├─ pdf_to_json.py      PDF → 分节骨架
│  ├─ translate.py        批量翻译 / 术语标注 / 术语表
│  └─ package.py          打分发 zip
├─ data/<slug>/           一篇论文的数据（你的论文放这里）
└─ reader/                阅读器
```

## 2. 第一步：把 PDF 拆成骨架

```bash
python tools/pdf_to_json.py ~/papers/some-paper.pdf my-paper
```

输出：

```
data/my-paper/
├─ 00-meta.json          论文元信息（标题先取文件名，需自己补 titleZh/authors）
├─ 01-front-matter.json  第一个检测到的标题之前的内容
├─ 02-introduction.json  ┐
├─ 03-background.json    ├ 每节一个文件，节内每段一个 pair，en 有值、zh 为空
├─ …                     ┘
└─ img/fig-03-1.png      论文里的位图（矢量图不会导出）
```

它怎么分节：按字号大于正文、或形如 `1`、`2.1`、`Introduction` 的标题行切开；
双栏排版的 PDF 会按「先左栏、后右栏」重排；连字符拆行会被拼回去。

**已知限制**（这些地方需要人/AI 收拾）：

- 表格会被拆成一堆碎段（数字散落），需要手工重建 `table` 块；
- 公式会变成 `ht = f(ht-1)` 这样的文本，需要改写成 `eq` 块；
- 扫描版 PDF 没有文本层，抽出来是空的 —— 需要先 OCR；
- 图注、脚注会和正文混在一起，需要人工判断归属。

## 3. 路线 B：脚本批量翻译

### 3.1 端点与模型

```bash
export OPENAI_API_KEY=sk-...                       # 必填
export OPENAI_BASE_URL=https://api.openai.com/v1   # 可选：换成 DeepSeek / 硅基流动 / 本地 ollama /v1
export MODEL=gpt-4o-mini                           # 可选：换成 deepseek-chat 等
```

只要服务端实现了 `POST /chat/completions`（OpenAI 兼容）就能用。

### 3.2 它到底翻译了什么

| 字段 | 是什么 | 处理方式 |
|---|---|---|
| `section.title` | 小节标题（从 PDF 抽出来是英文） | **翻译**；原文存进 `titleEn`，侧栏目录显示中文 |
| `section.lead` | 每节开头的「导读」框 | **不是翻译，是让模型写**：给它标题 + 开头两段英文，让它用 1–2 句中文说明这节讲什么、该注意什么 |
| `pair.zh` | 中英对照的右栏正文 | **翻译**，主要工作量（一篇 15 页论文约 120–150 段） |
| `sub.zh` | 子小节标题（如 `3.2.1 缩放点积注意力`） | 有 `en` 才翻 |
| `fig.zh` | 图注 | 有 `fig.en` 才翻 |
| `table.html` | 表格 | **不翻**，里面的数字必须原样；表头可自己写成「中文 English」 |
| `references` | 文献条目 | **不翻**，保留原文便于按标题检索 |
| `note` | 脚注 / 作者注 / 译者注 | **不机器翻**，这类内容通常要人写（比如指出原文自相矛盾处） |
| `en` | 左栏原文 | 永远不动 |
| `glossary` | 术语表 | 不碰；需要时用 agent 或 §3.7 生成 |

不会重复翻译：已有 `zh` 的段落会跳过，除非加 `--force`。

### 3.3 一次请求长什么样

发给模型的 system 提示词就是下面这段（`tools/translate.py` 里的 `SYSTEM`）：

```
你是一名技术论文译者，把英文学术论文逐段译成简体中文。要求：
1. 忠实、通顺，面向非专业读者；不添加原文没有的内容，不省略信息。
2. 专业术语首次出现时在中文后用括号保留英文，例如：注意力机制（attention）。
3. 保留所有编号引用（如 [12]、[3, 5]）、公式符号、数字、单位、变量名，原样不动。
4. 不翻译人名、机构名、模型名、数据集名。
5. 只输出一个 JSON 数组，元素是与输入逐条对应的译文，不要任何解释或 Markdown 代码块。
```

user 消息是把 `--batch`（默认 6）段英文编号后拼起来：

```
把下面 6 段英文逐条译成中文，输出长度为 6 的 JSON 数组：

1. The dominant sequence transduction models are based on …
2. We propose a new simple network architecture, the Transformer, …
…
```

返回必须是长度相同的 JSON 数组：

```json
["目前占主导地位的序列转换模型……", "我们提出一种新的、更简洁的网络结构……", "…"]
```

**校验**：条数不一致直接判失败；批量失败会自动降级成「一段一请求」重试；
单段也失败就跳过并打印警告，不阻塞其余部分。每批成功后立即落盘，中途断掉不会全丢。

### 3.4 成本与速度（粗略）

一篇 15 页论文约 6000 词 ≈ 8000 输入 token，译文约 6000 输出 token。
`gpt-4o-mini` 级别大约几美分、两三分钟；加 `--annotate` 和 `--with-terms` 会多出约 60% 的调用。
先用 `--dry-run` 看要处理多少段：

```bash
python tools/translate.py --slug my-paper --dry-run
# 待处理 19 项：fig 1、lead 5、pair 13
```

### 3.5 选项

| 参数 | 作用 |
|---|---|
| `--slug <名字>` | 必填，`data/<名字>/` |
| `--dry-run` | 只统计，不发请求（没配 key 也能跑） |
| `--force` | 重译已有的 `zh`（改过提示词后想重来） |
| `--batch 6` | 每次请求几段；长段落可调小，省钱可调大 |
| `--annotate` | 第二遍：给译文补 `[[术语|解释]]` 标记，见 §3.6 |
| `--with-terms` | 第三遍：由标记反查英文，生成 `terms.json`，见 §3.7 |
| `--model` / `--api-base` / `--api-key` | 覆盖环境变量，方便临时换模型 |

### 3.6 `--annotate`：让译文长出术语解释

没有 `[[术语|解释]]` 标记，阅读器里那个词就只是普通文字——**没有悬停解释，也没有点词高亮原文**。
这一步让模型在**不改动译文**的前提下就地加标记。

发给模型的 system：

```
你在为一份中英对照读物做术语标注。给你一段中文译文，请挑出 2-5 个值得解释的专业术语，
用 [[术语|解释]] 的形式就地包起来。要求：
1. 术语必须是译文里原样出现的连续子串；解释 1-2 句、面向非专业读者……
2. 只加标记，不要改写、增删、调序任何原文……
3. 不要标记人名、机构名、模型名、数字。
4. 直接输出加好标记的整段文字。
```

**关键的防呆校验**：把返回结果里的 `[[术语|解释]]` 还原成「术语」后，
必须与原来的译文**逐字相同**（只忽略空白）。模型只要动了一个字，这段就整段丢弃、保留原文。
所以 `--annotate` 最坏情况是「这段没标注」，不会把译文改坏。

效果：

```
标注前：每个词元先被投影成三个向量：查询、键和值。
标注后：每个[[词元|token：模型处理的最小单位，可能是一个词、一个子词片段。]]先被投影成三个向量：[[查询|query：这个位置「想找什么」。]]、[[键|key：这个位置「有什么」。]]和值。
```

### 3.7 `--with-terms`：生成中→英映射

「点中文术语，左边原文里对应的英文高亮」靠 `terms.json`。脚本从已标注的段落里收集中文术语，
把「英文原句 / 中文译文 / 候选术语」一起发给模型，让它回答每个术语对应的**英文原文**。

同样有校验：**这个英文串必须真的出现在同一段的 `en` 里**，否则丢弃。
匹配不上的词只是「点了不高亮」，不会报错。

```json
{
  "词元": "token",
  "多头": "heads",
  "当前最佳": "state of the art||state-of-the-art"
}
```

## 4. 路线 A（推荐）：让 agent 读论文并翻译

比跑脚本多出来的价值：agent 会**先读懂再写**——判断哪里该拆成两段、哪个词值得解释、
图注哪句该保留、表格对应的数字是什么；也会帮你把公式改写成 `eq` 块。

### 4.1 怎么发起

在仓库根目录对 agent 说：

> 读 `reader/FORMAT.md`，参考 `data/demo/` 的写法。把 `data/<slug>/` 里的英文翻译成中文，
> 逐句对齐，术语按下面规则加。做完跑 `python build_paper.py`，把 `!` 报错修完。

### 4.2 可以整段复制的提示词

> 你在维护一个「中英对照论文阅读器」。请先读 `reader/FORMAT.md` 和 `data/demo/` 里的示例数据，
> 理解 JSON 结构，然后完成 `data/<slug>/`：
>
> 1. **翻译**：每个 `pair` 的 `zh`。一句原文一段，长段落拆成 2–4 段，左右必须同指一事；
>    不合并、不省略、不补充。
> 2. **术语**：每个**首次出现**的专业词加 `[[中文术语|解释]]`。解释 2–3 句，先打一个生活化的比方，
>    再给严格定义，面向非专业读者；不要写「见 3.2 节」这种废话。同一个词只标一次。
> 3. **导读**：每节写 1–2 句 `lead`，说「这节要解决什么、读的时候注意什么」，不要复述原文。
> 4. **术语表**：写 `terms.json`，键是上面用过的中文术语，值是它**在同一段英文里原样出现的字符串**
>    （多种写法用 `||` 分隔）。写完逐条核对能在这段 `en` 里搜到。
> 5. **公式**：抽出来的 `f(x) = max(0, xW1 + b1)W2 + b2` 这类文本，改成 `eq` 块（属性用单引号，
>    分式用 `<span class='frac'>`），后面跟一个 `raw` 的「这个公式在说什么」白话解读。
> 6. **表格**：把散落的数字重建成 `table` 块，表头写成「中文 English」双语，数字必须与原文一致。
> 7. **图**：`img/` 里的位图，用 `fig` 块引用（`src` 写 `assets/<id>/文件名`），
>    图注中文 + 英文原注，再给 `labels` 列出图里英文字母的中文对照。
> 8. **注释**：原文的脚注、作者注翻成 `note` 块；原文自相矛盾或笔误的地方加 `译者注`，
>    不要私自改数字。
> 9. **校验**：跑 `python build_paper.py`，把输出的 `!` 全部修掉；再打开 `reader/index.html` 抽查。
> 10. **不要**把论文全文提交到公开仓库（见 `NOTICE.md`）。

### 4.3 人只做三件校对

1. **抽 5 段对照**：数字、`[n]` 引用、单位有没有被改动；
2. **点几个术语**：中文点下去，左边英文是否真的高亮（高亮不到 = `terms.json` 里那条写错了）；
3. **看图表**：表格数字与原文是否一致，图注有没有把 `Figure 3` 认错。

## 5. 构建与预览

```bash
python build_paper.py
```

它做三件事：

1. **校验**：`[[ ]]` 是否配对、`pair` 是否缺 `en`/`zh`、中文里是否混进英文双引号（会破坏悬停解释）；
   发现问题的行会以 `!` 开头打印，并以退出码 1 结束；
2. **打包**：把所有 `data/*/` 合成 `reader/papers/library.js`；
3. **复制插图**：`data/<slug>/img/*` → `reader/assets/<id>/`。

然后刷新 `reader/index.html`（双击即可，不用服务器）。

## 6. 书架与分组

书架是「所有论文的目录」，不只是已译的那几本。它由三部分拼成：

```
papers/                  PDF 原文件（本地放着，已在 .gitignore 里，不会进 git）
papers/manifest.json     书架目录：每本书的标题、分组、对应哪份译本
data/<slug>/             译本数据
```

`build_paper.py` 把 manifest 和 `data/` 合起来，生成 `window.SHELF`。
**判断规则**：manifest 里某项的 `slug` 对应的 `data/<slug>/` 存在 → 「已译」；否则「待译」。

### 6.1 往书架上加一本

1. 把 PDF 放到 `papers/`（文件名就用 arXiv 号，如 `2302.13971.pdf`）；
2. 在 `papers/manifest.json` 的 `items` 里加一条：

```json
{
  "arxiv": "2302.13971",
  "slug": "llama",
  "titleEn": "LLaMA: Open and Efficient Foundation Language Models",
  "titleZh": "LLaMA：开放高效的基础语言模型",
  "note": "开源模型的分水岭"
}
```

3. 跑 `python build_paper.py`，刷新页面。

- `slug` 先填好（比如 `llama`），等 `data/llama/` 建出来，这本书就自动从「待译」变成「已译」；
- `slug` 填 `null` 也行，那它会一直是待译状态；
- `optional: true` 用于「有数据才显示」的条目（示例论文就是这种）；
- `group` 可以不填：分组现在**由你自己在页面上建**，manifest 里的 `groups` / `group` 只当「第一次打开时的初始分组」用。

### 6.2 页面上的书架

- 左侧栏列出全部书目，灰点 = 待译；
- 点左上「书架 / Bookshelf」进全屏书架：分组、计数、搜索、卡片（节数 / 对照段 / 术语量 / 预计阅读时长 / 读到多少）；
- **分组自己起名字**：右上「＋ 分组」，或卡片右下角「移动到　＋ 新建分组…」。
  分组标题上可以「只看这组」「选择本组」「删除分组」；删分组不会丢书，书会回到「未分组」；
- **多选批量移动**：卡片右上角的小方框勾选（悬停才显示），底部浮出「已选 N 本 → 移入分组」；
  顶部「☐ 全选」勾选当前筛选/搜索结果里的全部；
- **阅读进度自动记住**：读到哪一节、百分之几、像素位置都存在本地，卡片上有进度条和「读到 42%」，
  点「继续阅读 →」回到上次的位置；
- 点右上「导出分组」会下载合并后的 `manifest.json`，覆盖回 `papers/manifest.json` 就能把分组固化下来；
- 待译卡片上的「怎么译？」会弹出该书的抽取命令；「PDF ↗」直接打开原文件。

> 分组和阅读进度只存在你自己的浏览器里（localStorage，键前缀 `br:`）。
> 换机器、换浏览器会回到 manifest 的初始分组；想让大家看到一样的分组，就把导出的 manifest 提交上去。

## 7. 打包分发

```bash
python tools/package.py --version 0.2.0
# → dist/bilingual-paper-reader-0.2.0.zip（阅读器 + 示例 + 工具，不含你的论文）
```

注意：`package.py` 只收 `data/demo/`，**你自己的论文数据不会被打进去**，这是有意的（见 `NOTICE.md`）。

同理，提交到 git 之前建议用**只含示例**的方式重新生成阅读器数据：

```bash
python build_paper.py --public    # 只打包 data/demo，library.js 与 assets 保持可公开
```

否则 `reader/papers/library.js` 里会带上你译的论文正文。

## 8. 一条命令走完

```powershell
.\make.ps1 -Pdf "C:\papers\paper.pdf" -Slug my-paper -Package
```
```bash
./make.sh ~/papers/paper.pdf my-paper --package
```

| 参数 | 作用 |
|---|---|
| `-Pdf` / 第一个位置参数 | PDF 路径 |
| `-Slug` / 第二个位置参数 | `data/` 下的目录名 |
| `-NoTranslate` / `--no-translate` | 只抽取，翻译自己来（路线 A） |
| `-Force` | 重译已有译文 |
| `-Package` / `--package` | 结束时打 zip |

没配 `OPENAI_API_KEY` 时脚本不会瞎跑：会先执行 `--dry-run` 告诉你多少段要翻，然后退出。

### 8.1 把书架上的论文一次译完

`tools/batch.py` 按 `papers/manifest.json` 排队，把还没译的一篇篇跑完（抽取 → 翻译 → 术语 → 构建）：

```bash
python tools/batch.py --dry-run          # 还差几篇、都是哪几篇
python tools/batch.py                    # 全都译了
python tools/batch.py --only 2302.13971  # 只译一篇
python tools/batch.py --limit 2          # 先来两篇试试
```

- 每篇跑完就落盘，失败只影响那一篇，重跑自动跳过已译的；
- 抽取完会把 `manifest.json` 里的中英标题、分组、arXiv 号补进 `data/<slug>/00-meta.json`；
- 中文标题、术语解释的质量不如路线 A（agent 通读后写），适合先出草稿再润色。

## 9. 质量控制清单

- [ ] `build_paper.py` 没有 `!` 输出
- [ ] 「仅译文」模式通读一遍：有没有半截英文、有没有「〔译〕」之类的占位残留
- [ ] 抽查数字与单位：`28.4`、`100,000 steps`、`3.5 days` 这类不能被改写
- [ ] 点 3 个术语：解释能看懂，且左栏英文同步高亮

## 10. 常见问题

| 现象 | 原因 / 处理 |
|---|---|
| `401 / invalid api key` | `OPENAI_API_KEY` 没设或过期；确认 shell 里 `echo $env:OPENAI_API_KEY` 有值 |
| `429 / rate limit` | 调小 `--batch`，或换模型；脚本自带 3 次退避重试 |
| `返回条数不符` | 段落里有超长公式或表格，模型合并了条目；把 `--batch` 调到 2–3 再跑那段 |
| 译文里有英文双引号 | 会破坏 `data-tip`；`build_paper.py` 会报 `!`，改成「」 |
| 章节切得乱七八糟 | 扫描版/多栏/大量公式的 PDF 常见；把 `NN-*.json` 手动合并或拆分即可，文件名顺序就是书里的顺序 |
| 图不显示 | `src` 必须是 `assets/<meta.id>/文件名`，图片放 `data/<slug>/img/` |
| 术语一个都没生成 | 译文里没有 `[[…]]`；先跑 `--annotate`，再 `--with-terms` |
| 点术语，原文没高亮 | `terms.json` 里那条英文在该段 `en` 中找不到（大小写/单复数/连字符要一致） |
| 中文变方块 | 系统缺 `Noto Serif SC`，回退宋体；Windows 自带宋体，一般没问题 |
